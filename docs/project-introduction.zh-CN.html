AGENT ENGINEERING / 从设计到验证

让 Agent 的工具调用
真正可恢复

Durable Tool Runtime：把业务意图、执行责任与副作用证据，放进同一套可检验的契约。

人机共创 · 设计与实验记录2026 年 9 月 11 日内容基线 1729c0e · MIT

一个 Agent 重启，重新加载对话，又开始调用工具。这能说明任务已经恢复了吗？我们用一个可运行的框架雏形，把这个问题拆开验证：进程可以重新启动，业务责任却不能重新算起。

01 / THE PROBLEM

缺的不是一句“继续执行”

当工具只是计算或检索，恢复上下文通常有助于继续工作。但当工具会预留库存、创建资源、上传文件或发送消息时，事情多了一层：Agent 说自己做过，不等于外部业务已经发生；没有收到结果，也不等于副作用没有生效。

设想一次库存预留。业务服务已经扣减库存，响应却在返回途中丢失。调用方看到超时，业务方已经成功。重新执行整项任务，可能制造第二笔预留；直接宣布完成，又缺少调用方已经取得的证据。

而且，中断可能发生在不同地方：Agent 退出时 worker 仍在执行；worker 退出时下游已经提交；完成结果已经落盘时，调度器还没来得及消费。这些状态不能都被压成“任务失败”，再交给整体重跑。

我们真正想接续的，
是原业务身份与已经承担的责任。

这就是 Durable Tool Runtime 的出发点：通过 MCP 接入 Agent，将有副作用的工具调用建模为持久化业务操作，并为授权、执行、对账、补偿提供统一的约束路径。

这里并不是说 MCP 没有相关描述。它已有只读、破坏性、幂等性等工具提示，以及任务增强执行能力。但这些声明不会自动让业务变更、幂等记录和回执一起提交。我们要补的是由谁实现、在哪里检查、失败后怎么办的执行契约。

协议边界：MCP 工具注解与执行属性。本文是本地 POC 的设计实践，不提供任意外部接口的 exactly-once 保证。

02 / THE ARCHITECTURE

把工具调用，升级为业务操作

我们把相对稳定的部分留在业务治理核心：批准内容、授权范围、操作状态和证据规则。将任务注入、工具接入、运行监督等差异留给 runtime 接线。

业务方定义“什么叫正确”，框架把这些规则落实到执行路径。业务工具定义者不应为了更换 Agent runtime，重新定义同一套业务语义。

最先分清的，是几个不同的“状态”

Task 是目标，Run 是一次 Agent 运行，Grant 是当前允许做什么，Operation 则是平台已经接下的具体工作。它们可以放在同一个数据库里，却不能共享一个笼统的成功或失败标记。

Task / Intent
目标与获准业务动作。恢复时保留身份，不随进程重启制造新意图。
Run
一次 Agent 运行。丢失后可以建立后继 Run，并保留与前序的关系。
Grant
当前命令权限。包含明确意图集合和动作范围，不能从旧上下文恢复权限。
Operation
已持久受理的工作。调用者退出后，它仍须被处理或明确说明阻塞。

工具定义必须被执行路径消费

库存工具的定义不仅包含输入 schema，还声明异步持久执行、已批准意图授权、下游原子提交要求，以及“对账或阻塞”的未知结果策略。

implementationRef 由可信 Catalog 查找已注册实现，绑定参数校验、业务键生成和证据判定。Core 在受理时消费授权规则；worker 在执行和恢复时消费结果规则。定义与实现不匹配时停止推进，不拿新逻辑盲目解释旧操作。

这不是“写上幂等就拥有幂等”。同一身份如何生成、参数变化如何拒绝、业务效果与回执怎样一起提交，仍需具体实现与测试。当前是一个库存适配器和静态注册表，不是任意工具上传后就自动获得保障的平台。

责任从“持久受理”开始

请求到达 Core 后，先检查 Grant、当前命令资格、意图集合、批准参数和实现版本。首次受理时，Operation、初始事件与待投递记录在同一个本地事务里提交；同一获准意图的重复请求则返回原 Operation。

关键边界 / DURABLE ACCEPTANCE

发出命令，不等于平台接下责任。持久受理之后，责任才成立。

ACCEPTED 只说明工作已经被接下，不代表业务已成功，也不承诺在任意故障下最终一定成功。

受理响应如果丢失，调用者可以按原意图查询或幂等重提。但它不应因为换了一个 session，就把原工作重新定义成另一笔业务。

03 / TWO LIFECYCLES

授权可以到期，责任不能一起消失

Agent 崩溃时，worker 可能还在执行；worker 崩溃时，Agent 的权限可能仍然有效。更换其中一个，不应迫使另一个也从头开始。

这个判断不仅用于处理故障。调用者失去发起新命令的资格，并不自动撤销平台已经受理的工作。 撤销业务目标需要明确的取消流程，而不是由断连或凭据过期隐式推断。

task_epoch + Grant

谁还能发起新命令？

约束 Agent 的当前命令资格。换代拒绝旧命令，但不抹去已受理操作。

executor_epoch + 租约

谁还能提交执行结果？

约束某个 Operation 的 worker。新执行者接管后，旧结果不能覆盖权威状态。

租约只说明当前授予谁资格，不证明旧进程已经停止。旧进程可能从长暂停中恢复，旧请求也可能已经在途中。因此，治理账本的 epoch 检查不是所有远端资源通用的 fencing token；副作用安全仍取决于下游幂等、条件写或等价约束。

恢复业务，不一定要恢复原会话

新 runtime 未必读得懂旧 session，但仍可以通过新的 Run，围绕原意图与 Operation 接续。反过来，原 session 能打开，也不代表业务结果已经对账。

我们希望 runtime 差异集中在接线层。不过当前 runner 仍直接创建 CodexRun，绑定中也有 codexBinary。面向多 runtime 的分离是设计方向，第二种 runtime 的等价验收尚未完成。

调度器自身也要能重启

如果旧 Run 的引用只存在于调度器内存里，恢复链路仍会断。我们把 Run、当前任务关联和前序关系持久化，由独立 runner 监督 Agent 并记录结果。替代调度器重新发现工作：已有完成证据就消费它，确需接续才创建后继 Run。

当前依赖同机 PID、启动身份、进程组和 SQLite。跨机调度需要重新验证网络分区、时钟、持久存储与远端控制，不能把“方法论可复用”写成“实现已经可直接搬过去”。

04 / THROUGH THE FAILURE WINDOW

走过一次真实断点

用一笔库存预留串起这套设计：初始库存 10，批准预留 3；下游提交后杀掉 worker；恢复原操作，再执行取消。原预留记为 O1，补偿记为 O2，业务回执记为 R1。

先说明证据范围

下面主线来自 npm run demo：真实 MCP、HTTP、SQLite 与子进程，调用端是确定性程序，没有运行模型。原生 runtime 与前序真实模型实验单独列在后文，不拼接成一条虚构经历。

这个窗口是案例的核心。实验控制器能直接检查库存，知道可用量已经变成 7；但恢复 worker 不能偷用裁判视角，必须通过它获准使用的接口取得业务证据。

库存回到原值，不等于什么都没发生

最终 O1 仍为 APPLIED，表示预留发生过；O2 为 APPLIED，表示补偿完成；最新记录的业务观察是 RELEASED。三者并不矛盾，分别描述历史执行、补偿执行和业务状态。

05 / EVIDENCE, NOT JUST A PASS

记录留下之后，还要知道它能证明什么

工具日志能重建系统当时观察和记录到的轨迹，不一定覆盖完整现实：调用可能还没生效，业务也可能已经提交但回执未归档。日志中没有成功响应，不能单独证明没有执行。

这并不意味着日志没有证据价值。可信业务回执，或与业务变更原子提交的权威记录，都能提供证据。区别不在于文件叫日志还是单据，而在于谁记录、记录什么、与业务提交有什么关系。

持久化，解决记录能否留下。
证据契约，解决记录能证明什么。
恢复策略，决定据此可以做什么。

本 POC 的 Checkpoint 是操作引用入口，不是进程快照。恢复仍要按当前 Grant 过滤并读取事实。更频繁地保存 Checkpoint，也不能单独消除“业务已提交、治理结果未记录”的间隙。

“未知”因此必须约束行动。查询暂时没有记录，也未必意味着在途请求不会生效。不能对账、又不具备安全重试条件时，系统应明确停住。可靠性不仅体现在能继续，也体现在知道何时不应继续。

三种验证，不能混成一种证据

验证层实际内容证明到的范围
核心与默认演示真实服务、数据库、子进程；无模型已覆盖的契约与故障窗口
原生运行时＋模拟模型真实 Codex 进程，模拟响应指定环境的接线、进程恢复与证据通路

公开代码 1729c0e 的 Linux/macOS CI 各通过 50 项测试及默认演示。原生模拟测试在行为候选 e9dd1b0 上通过四个冷启动窗口，之后只调整文档与 usage-help；验证环境为 Node.js 24.16.0、Codex CLI 0.153.4 与 macOS。

其中，独立的 after_commit 场景终止了 scheduler、runner 和 worker。替代调度器从持久状态建立后继 Run，最终仍只预留一次。它是另一场实验，不能与上文的无模型演示拼成同一次运行。

公开导出版本没有新跑真实 API-key 模型验收。 早先的真实模型记录属于研究版本，不能挪用为当前 SHA 的全新证明。

请求尝试不一定等于完整模型响应或计费单位。一次 episode 内接续原意图与数据库是恢复；新建目录重跑场景是补验，不是原任务恢复。并发实验使用独立业务存储，共享资源争用另有确定性测试；二者都不等于持续生产负载。

私有原始轨迹未公开，历史汇总的独立可审计性因此弱于完整数据集。公开可复现部分是源码、测试和新运行生成的报告。

几次失败，反而把框架讲清楚了

授权范围曾经太宽。 早期 Grant 只绑定 task 与动作 scope，旧 token 能执行同一 task 后来新增的意图。新的反例揭示了旧测试没有覆盖的问题，随后加入不可变意图集合，并统一约束提交、读取、取消和 Checkpoint。

裁判也会误判。 一条实际收到的授权拒绝，因为原生工具事件标记 failed 而被丢弃。正确修复是让裁判识别拒绝证据，而不是要求模型继续尝试直到看起来成功。另一次最终快照早于 worker 收尾，修正后才使报告对应执行停止后的事实。

导出后的接线必须重新验证。 公开版先后暴露了模拟夹具丢失工具命名空间、误解析计时包装的问题。第二轮业务只预留一次，协议却仍未完成。两处都增加具体回归并复验原生路径，而不是拿私有版本曾经通过当作替代。

还有一条历史传输错误在定向补验里没有复现，其原始根因仍然未知。补验成功不是根因证明。

06 / A BASELINE TO BUILD ON

把边界说明白，才有下一步

日志与恢复并不是新问题。Apache Maka 的文档强调 append-only RuntimeEvent、上下文与界面的日志投影，以及统一 Runtime Host 的执行权威。它是相关的设计思路；本文不做同条件横向评测，也不据此宣称我们的方案更强。

我们的切入点更具体：围绕有副作用的业务工具，把批准意图、命令授权、持久受理责任、业务证据和补偿规则组织成可验证路径。现在得到的是可运行的模块与不变量，而非成熟的通用平台。

接下来的方向很明确：提取通用 runtime 接口并验收第二种接线；完善工具定义的版本与能力协商；接入真实弱能力下游；再对跨机和持续并发进行独立验证。这些是迭代方向，不是当前完成清单。

部署边界

当前假设主机、数据库、Controller 和实现注册表可信。不覆盖恶意同用户进程、数据库管理员篡改、公网服务加固或数据库整体丢失。不要把本地示例直接暴露为生产服务。

从一个可复现的案例开始

默认演示需要 Git、Node.js ≥24.16.0、内置 SQLite ≥3.51.3。进程控制以 POSIX 为目标，不支持 Windows；不需要模型账号或 Codex。

git clone --branch baseline/v0.1 \
  https://github.com/funkdog/durable-tool-runtime.git
cd durable-tool-runtime
git checkout 1729c0e4b1835e72422fe675d1d9af96330817be
npm ci --ignore-scripts --include=dev

原生模拟测试、真实 API 验收是另外两条入口。后者必须显式启用，并提供专用 API key、模型和预算。实验生成的凭据、数据库和轨迹不应提交到仓库。
